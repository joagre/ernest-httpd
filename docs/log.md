## What the server leaves out

*2026-10-27.* A request's body is refused, 413, since nothing on the site takes input over HTTP, and with it chunked request decoding and `Expect: 100-continue`. No response is chunked, since every file has a size. There is no `Cache-Control`, since `Last-Modified` and 304 make a revisit a cheap check; headers by path wait for a measured need. A WebSocket negotiates no extension and no subprotocol, which the page asks for none of. Principle 5.

Compression waits until a first visit is measured slow. Its shape is known and changes nothing of the server: the site's generator writes `page.html.gz` beside `page.html`, and the server sends it where `Accept-Encoding` names `gzip`, with `Content-Encoding: gzip` and `Vary: Accept-Encoding`, compressing nothing itself. There is no rate limit on requests: a static file is cheap, the shells have their caps and their start limit, and a flood past these is the network's to stop. At the connection cap the excess waits at the kernel, and no 503 is answered, which would spend work on the clients there are too many of.

## What the server takes from a client

*2026-10-27.* The path is decoded before its check, so that `/%2e%2e/` is refused as `/../` is. `%2F` is refused, since no name on the site holds one. A name beginning with `.` answers 404, so that nothing like a `.git` or an editor's backup is ever served. Two `Host` headers or a folded header answer 400, and with bodies refused, request smuggling has nothing else to work with. A redirect is built from the configured host alone, so that a forged `Host` cannot make the server a redirector to anywhere. `Origin` is checked, since a WebSocket is not held to the browser's same-origin rule. Principle 1.

## A container per visitor

*2026-10-13, decided 2026-10-26.* Measured on an eight-core machine on 2026-10-13: a bare `erl` is 71 MB, a bare Ernest node listening 87 MB, and a program's run 72 MB at its peak and 0.6 seconds from start to exit, so a visitor's shell is a BEAM of about 90 MB that starts in under a second. The Go and Rust playgrounds run each submission in a fresh sandbox, a container or a VM, with time, memory and output limits, no network, and nothing kept. Try Elixir, Try OCaml and Jupyter's kernels run one process per visitor behind a web terminal. No system known runs strangers' sessions on one shared runtime without a process-level wall, and those that share one trust their users. So each visitor has a container of their own (principle 1); *The machine* sizes the cap from this number.

The language is whole in the container, no module forbidden, since nothing done through `Fs`, `Os`, `Tcp` or a `foreign fn` leaves it, and a shell with fewer modules would be a second mode of the language that the guide's examples would not run in (principle 2). The image holds nothing secret, since a `foreign fn` reads the image and the environment. `--network none` keeps the loopback, so that the guide's `Tcp` examples, which talk to themselves, run. There is no pool and no manager: a process per session owns its command under a terminal, and pre-started containers are decided only if a container's start is measured slow (principle 5). The server knows terminals and not containers: the container is the command's, so the server stays a general one, a static site and web terminals, and nothing of ernest-lang.org's sandbox is in its code (principle 2).

## The session's shape

*2026-10-27.* A session outlives its connection, since moving to another page closes the WebSocket and the site keeps a visitor's shell across pages. It starts at the page's first resize, so that the shell starts at the panel's size and not at a guessed one. Its lifetime is five minutes from the last key or Extend, one deadline that either moves. It replaced an idle time with a key's answer and a total of 30 minutes: Extend serves a visitor whose program runs without typing, and there is no total cap, since a session kept alive holds one of the shells the cap allows and no more (principle 5). Starts are counted by remote address and not by cookie, which a visitor resets by clearing it. The cookie is set on the 101 alone, so that the static pages set none and the privacy line can say that the shell alone does; it is drawn from `Crypto.randomBytes`, so it cannot be guessed.

## Item 2: the listener, the connection and the access log

*2026-11-02.* `Listener`, `Connection`, `AccessLog` and the entry point serve the site over plain HTTP, each design section written before its code and cited by its tests. The design as first written had the entry process close the listening socket from outside, and that fails on Ernest's model of a socket: E.18 has a call on a socket another process has closed fault, as a call on an ended process does, where only a call waiting at the close answers `Closed`. So each socket is called by one process and closed by it. The listener spawns an acceptor, which alone calls `Tcp.accept`, one connection for each `Accept` the listener sends; the listener waits on its mailbox alone and takes a `Stop` at once, kills the acceptor, waits for its end, closes the socket and kills its idle connections, each serving one ending once its response is written. A first build had the listener itself accept in rounds of the idle deadline, which made a stop wait up to a minute; a static site that restarts in about a second decided against it, principle 3: a wait that can hold a `Stop` hides one. The feedback's line 5 asks Ernest for `Left(Closed)` after a close.

A listener that ends before the end is a failure of the program: the entry process stops the others, has the log write what it holds, and faults, `a listener ended: ` and the reason, which ends the program with a status that is not 0. It cannot call `Os.exit`, since a subscriber of `Os.termination` that exits waits for its own reply forever, the feedback's line 6; spawning a process to call `Os.exit` was rejected as a way around the gap (CLAUDE.md, *Defects and gaps*). The rest the build decided, each a sentence now: the configuration read within 5000 ms, no deadline being configured before it is read; the listener's address an argument of `Connection.serve`, since only the listener has it, with `Server` what every connection shares (principle 3); `Content-Length` one number in digits; a refused `HEAD` with no body through `Static.withoutBody`; a failed write logged nowhere; the entry told before `ResponseWritten`, so the end's kill loses no line; a kept 1.0 response saying `Connection: keep-alive` (principle 1); and the configuration's headers naming none of the four the server writes itself, so that a configured `Content-Length` cannot break every response's framing (principle 3). The write deadline's promise under a host that takes a write whole, the feedback's line 7, is the plan's decision for item 5.

The access log is in UTC, so that the logs of two machines agree and the library needs no time zone, and its batches are what has arrived while it wrote, with no timer.

## Item 4: the WebSocket, the shell and the sessions

*2026-11-02.* The live shell is served: `WebSocket` is RFC 6455's framing, `Shell` a connection's life after its upgrade, `Sessions` the sessions by cookie and `Session` one visitor's program under a terminal, the design's §10 to §12 written before their code and cited by their tests, with their seams in §2, §6 and §7. Two agents built them at once on disjoint files, the frames against §10's code block as the contract. Ernest names a module by its file, so the module stands in `src/web_socket.ern` and keeps the protocol's name, which a reader predicts (principle 1).

The shape is the listener's again: Ernest's reads block their caller, and a probe showed a write from another process going through while a read waits, on a socket and on a terminal alike. So a shell reads its socket through a reader process and a session its terminal through one, each owner waiting on its mailbox alone, and a reader is killed before what it reads is closed. A detached session asks for no read, so its program blocks on output as on a full terminal, the proposal's rule, and the one piece a read answers after a detach is held for the next shell.

The lifetime is one alarm at a time, set for the warning's time and then the end's, and set again where a key moved the time, so that a key costs no call to the clock and no stale alarm is counted (principle 5). A program's end has a deadline of its own, `shell.hangup`: the terminal is hung up as a closed window hangs it up, and the program is killed where it has not exited in time, since killing podman at once would leave its container running. The entry process stops the sessions before the listeners, and the listener never kills a shell: a connection tells it `Upgraded`, and at the stop it tells the shell to close with 1001 as a session does, so that no reader is left in a read on a dying socket.

The build corrected the design in four places. A session's reader reads to the end as well: a killed reader's read is still answered, taking the output or the exit, so the end hangs the terminal up and reads on through the reader until the exit or the hangup's deadline, and kills the reader only then (principle 2).

The reader's answer is `Answered`, since a module's constructors are one name each and `Read` is the request. A shell holds what it means for its session while the attach is under way and sends it in order once attached, since the page is not told when the attach completes and its first keys were lost (principle 1). A session tells the sessions as its end begins, so that the page's Restart, a Stop and a new connection within the hangup, starts a new session instead of meeting the ending one.

`WebSocket` answers an error at the bytes that show it, a header before its payload, so a client's claimed length is no memory the server gives it; a length not in its shortest form is refused as the RFC's MUST; and `encode` writes a message as given, an `Optional` giving every write of the shell's an arm no value reaches (principle 3). Its masking loop's `_` for the end of the bytes is the second such site after `Static.percentDecoded`, the count the *Bitstrings* verdict asked kept. Two lines go to Ernest, 10 and 11: a program's process ends at its `Exited`, so a write as the program exits faults the session, which the page sees as 1011 with a trace where 4004 is due, a gap the plan carries; and a read whose caller has ended is answered to no one. `make test` went from 7.3 to about 12 seconds for 55 more cases, the real deadline waits of the session's and the shell's tests among them, already shortened; the rest is four more modules and the end-to-end shell.
