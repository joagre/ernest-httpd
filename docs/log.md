## Item 1: the configuration and the static site

*2026-11-02.* `Config` and `Static` are functions over their reads of the file system, as the plan's item 1 asked, each a section of the design written before its code and cited by its tests. What the sections left silent the build decided and wrote back as a sentence each: a top-level value that is no object is `the configuration`'s; members are checked by their names' code points and a row's rules in its order, since a `Map` keeps no source order; a target is read by code point; a scheme is RFC 3986's and an authority ends at `?` too; `..` is answered before a dot segment; a 301 has no body and its `Location`'s leading slashes are made one; a file asked for as a directory is 404; a `404.html` the file system refuses is 500.

Principle 1, least surprise, decided the two that matter. A reader predicts that `/` splits a path wherever it stands, but `String` matches by grapheme, and a `/` followed by a combining mark escaped the root through `Path.join`; the path is split by bytes. A reader predicts that a redirect stays on the site, but `//docs` written back as `Location: //docs/` names another host. Both are tests now. The rules on the configuration are every one the proposal's example implied and no more, a member of no field refused so that a misspelling is not silently ignored (principle 3); `shell` alone may be absent, since a static site costs nothing for a feature it does not use (principle 5). What answers 500 where 404 is due, a path through a regular file, a name too long and a loop of links, waits on `Fs` naming those cases, the plan's gap and the feedback's line 1.

## Item 2: the listener, the connection and the access log

*2026-11-02.* `Listener`, `Connection`, `AccessLog` and the entry point serve the site over plain HTTP, each design section written before its code and cited by its tests. The design as first written had the entry process close the listening socket from outside, and that fails on Ernest's model of a socket: E.18 has a call on a socket another process has closed fault, as a call on an ended process does, where only a call waiting at the close answers `Closed`. So each socket is called by one process and closed by it. The listener spawns an acceptor, which alone calls `Tcp.accept`, one connection for each `Accept` the listener sends; the listener waits on its mailbox alone and takes a `Stop` at once, kills the acceptor, waits for its end, closes the socket and kills its idle connections, each serving one ending once its response is written. A first build had the listener itself accept in rounds of the idle deadline, which made a stop wait up to a minute; a static site that restarts in about a second decided against it, principle 3: a wait that can hold a `Stop` hides one. The feedback's line 5 asks Ernest for `Left(Closed)` after a close.

A listener that ends before the end is a failure of the program: the entry process stops the others, has the log write what it holds, and faults, `a listener ended: ` and the reason, which ends the program with a status that is not 0. It cannot call `Os.exit`, since a subscriber of `Os.termination` that exits waits for its own reply forever, the feedback's line 6; spawning a process to call `Os.exit` was rejected as a way around the gap (CLAUDE.md, *Defects and gaps*). The rest the build decided, each a sentence now: the configuration read within 5000 ms, no deadline being configured before it is read; the listener's address an argument of `Connection.serve`, since only the listener has it, with `Server` what every connection shares (principle 3); `Content-Length` one number in digits; a refused `HEAD` with no body through `Static.withoutBody`; a failed write logged nowhere; the entry told before `ResponseWritten`, so the end's kill loses no line; a kept 1.0 response saying `Connection: keep-alive` (principle 1); and the configuration's headers naming none of the four the server writes itself, so that a configured `Content-Length` cannot break every response's framing (principle 3). The write deadline's promise under a host that takes a write whole, the feedback's line 7, is the plan's decision for item 5.

## Item 3: TLS, the redirect listener and the hosts

*2026-11-02.* The server listens over TLS and on the redirect listener, and a request's host decides before the site serves it, the design's §2, §6 and §9, each section written before its code and cited by its tests. TLS asked nothing of the connection: E.18 runs the handshake in the socket's process at the first read, within that read's deadline, and `Tcp.remote` answers before it, so a connection serves a plain and a TLS socket by one code and only the redirect listener's kind reaches it, as the challenge site in `Server`, one value for each listener (principle 3: a connection learns what it serves from a value, not by asking which listener it is).

`Hosts` is a module of its own, the one place the canonical host, the redirect hosts and the challenge are decided, asked before `Static.serve` (principle 2). The challenge is served by `Static` from a site of the directory's `.well-known/acme-challenge` below it, so that the directory is what certbot's webroot option takes and one piece of code serves files; a 301 of that site is made 404, a challenge being a file. `Static` exports its reading of a target, `pathAndQuery` and `authority`, so that the hosts read a target as the site does.

The build decided, each a sentence now: a request's host is an absolute-form target's authority before its `Host` header, as RFC 9112 has it, and a request naming none is the canonical host's; the port dropped is a `:` and digits alone at the host's end, after its last `]`, and any other tail stands, so that `ernest-lang.org:abc` matches no host and answers 421 rather than being served as the canonical one (principle 1, with no status added); the configuration's hosts lose their ports the same, so that a deployment on another port is served and redirected to `https://` and the host as written, the dropping `Config`'s, `withoutPort`, since `Hosts` reads the configuration and the build refuses a cycle (§11.1), and a `:` with no digits dropped too, RFC 3986's empty port.

A redirect host that is the canonical host is refused at the start, §4, since it would redirect to itself; `/` stands for an absolute-form target's empty path before its query.

The 421 and the 301 answer any method, a `HEAD`'s body dropped. Two feedback lines, 8 and 9: `Verified` refuses a self-signed far end whose certificate the file holds, and `listenTls`'s refusal is the host's Erlang term.

The test certificate is a self-signed EC P-256 pair held as text in the tests of `Connection` and `ErnestHttpd` and written under the scratch directory, its key made the user's alone, so that no key's file stands in the repository. `make test` went from 6.2 to 7.0 seconds for 16 more cases, the host's TLS starting in the test runtime and in the program; the plain form stays. `Connection` and `Hosts` each keep a one-line `headed`, a `HEAD`'s body dropped, rather than a third exported function for one line.

## Item 4: the WebSocket, the shell and the sessions

*2026-11-02.* The live shell is served: `WebSocket` is RFC 6455's framing, `Shell` a connection's life after its upgrade, `Sessions` the sessions by cookie and `Session` one visitor's program under a terminal, the design's §10 to §12 written before their code and cited by their tests, with their seams in §2, §6 and §7. Two agents built them at once on disjoint files, the frames against §10's code block as the contract. Ernest names a module by its file, so the module stands in `src/web_socket.ern` and keeps the protocol's name, which a reader predicts (principle 1).

The shape is the listener's again: Ernest's reads block their caller, and a probe showed a write from another process going through while a read waits, on a socket and on a terminal alike. So a shell reads its socket through a reader process and a session its terminal through one, each owner waiting on its mailbox alone, and a reader is killed before what it reads is closed. A detached session asks for no read, so its program blocks on output as on a full terminal, the proposal's rule, and the one piece a read answers after a detach is held for the next shell.

The lifetime is one alarm at a time, set for the warning's time and then the end's, and set again where a key moved the time, so that a key costs no call to the clock and no stale alarm is counted (principle 5). A program's end has a deadline of its own, `shell.hangup`: the terminal is hung up as a closed window hangs it up, and the program is killed where it has not exited in time, since killing podman at once would leave its container running. The entry process stops the sessions before the listeners, and the listener never kills a shell: a connection tells it `Upgraded`, and at the stop it tells the shell to close with 1001 as a session does, so that no reader is left in a read on a dying socket.

The build corrected the design in four places. A session's reader reads to the end as well: a killed reader's read is still answered, taking the output or the exit, so the end hangs the terminal up and reads on through the reader until the exit or the hangup's deadline, and kills the reader only then (principle 2).

The reader's answer is `Answered`, since a module's constructors are one name each and `Read` is the request. A shell holds what it means for its session while the attach is under way and sends it in order once attached, since the page is not told when the attach completes and its first keys were lost (principle 1). A session tells the sessions as its end begins, so that the page's Restart, a Stop and a new connection within the hangup, starts a new session instead of meeting the ending one.

`WebSocket` answers an error at the bytes that show it, a header before its payload, so a client's claimed length is no memory the server gives it; a length not in its shortest form is refused as the RFC's MUST; and `encode` writes a message as given, an `Optional` giving every write of the shell's an arm no value reaches (principle 3). Its masking loop's `_` for the end of the bytes is the second such site after `Static.percentDecoded`, the count the *Bitstrings* verdict asked kept. The plain forms stay measured: masking 64 KiB costs about a millisecond each way.

Two lines go to Ernest, 10 and 11: a program's process ends at its `Exited`, so a write as the program exits faults the session, which the page sees as 1011 with a trace where 4004 is due, a gap the plan carries; and a read whose caller has ended is answered to no one. `make test` went from 7.3 to about 12 seconds for 55 more cases, the real deadline waits of the session's and the shell's tests among them, already shortened; the rest is four more modules and the end-to-end shell.
