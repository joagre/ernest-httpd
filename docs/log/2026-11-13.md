# Decisions, 2026-11-13

## The shell's reader asked

*2026-11-13.* A reading of `docs/design.md` from outside the project found seven things. One is built, the shell's reader; two were the design's wording; two wanted a regression test each; and two are dropped. The architecture stands as it was read.

The shell's reader read on unasked and told the shell each message, and the shell can wait in one write for the whole write deadline. A client that sent pings and left their pongs unread grew the shell's mailbox meanwhile: in a probe, 64 MB of pings took the server from 113 MB to 391 MB, and no write of the client's was held. A call's wait reads the caller's mailbox (report §10), so each write grew slower as the mailbox grew, and a drain of 256,000 waiting messages did not end in three minutes. What the shell held for its session while an attach was under way grew the same way.

The reader now answers each `Read` with one message, `Received` holding what one read completed, and the shell asks again once it has handled the answer (design §11). Its mailbox holds one answer of the reader's at most, and what it has not handled waits in the socket, which holds the client: the same client was held after 4.6 MB, the server at 112 MB. There is no cap and no counter. The read is the brake, as the session's reader brakes its terminal (§12), one way for both (principle 2). One read answered 9,216 bytes at most, about 70 pings, which E.18 does not state: line 30.

The shell passes keys to its session as fast as it handles them, with no answer awaited. The session's mailbox is §12's: a session waits in no call but its end's, so it takes keys as they come and drops what passes the message limit.

While an attach is under way the shell asks for no read, so what it holds for the session is what followed the first resize in one `Received`, and it waits on the attach's answer alone, which §12 gives every attach. The text before closed that state at the idle deadline, for a client that sent nothing; a client that sent was held without end. A session that faults before it answers now leaves its shell until the stop, the client's close unseen. A deadline on the attach was weighed and left out: the fault is the defect, and a second mechanism for a state the design does not admit is one more thing to read (principle 5).

A reader that waits for a `Read` outlives a shell that faults, since a process the program spawns belongs to no one (report §6.9), where the reader before ended on its read of the dead socket. So the shell's reader monitors its shell and returns at its end where it waits for a `Read`; in a read it ends by the read's fault, as before. The session's reader and writer wait the same way and are a step of the plan's.

The wording. §10 said that the messages completed before an error "go with it", meant as lost with it and read as answered with it; it says dropped, which the decoder did and a test held (principle 1). §11 sent `Set-Cookie` "where the request carried no cookie", the glossary's cookie, read as no `Cookie` header; it is sent where the cookie is drawn, a request whose every `shell` cookie is of another form among them. §11 was silent on a reader that ends otherwise than by returning, and says the shell closes.

§5 follows a link out of the root, and says so. The root is no confinement: nothing writes under it while the server runs, and whoever can place a link there can place the file. nginx and Apache follow links by default. A check at the open would be a rule every request pays for a site the operator installs (principle 5). A regression test holds a link out of the root, where only a loop was tried.

Two more regression tests: a `Close` and then keys in one write, the keys never reaching the session, which a `Received` handled in order now states; and a whole `Binary` before a frame the RFC forbids, the error answered alone. A `Close` and a malformed frame in one read answer 1002, where two reads answer the `Close`: the client broke the protocol either way, and the decoder keeps one rule.

Dropped: the tests under load, each already decided or bounded, the largest file against the caps (*The caps on 0.10.0*), the stop within `TimeoutStopSec` (§13), the restart at the cap (*Milestone 2, items 3 and 4: the attach's word and a restart at the cap*), and the access log's lines, which wait at most the requests of one file deadline; and the matrix of refusals, whose rows are §4 to §11's tests but for the two above, the container's rows being the rehearsal's. `make test` takes about 18 s where it took 17.5, for six more cases.


## The session's helpers

*2026-11-13.* A session's reader and its writer waited for a `Read` and a `Write` without end, so they outlived a session that faulted or was killed, since a process the program spawns ends with no other (report §6.9). Each now monitors its session before its first wait and returns at its end where it waits, as the shell's reader does its shell (*The shell's reader asked*, design §12). It is one way for the three (principle 2).

In a read or a write a helper ends by the call's fault, the program ending with its session (Appendix E.23). A probe on `ern 0.10.0` killed a program's owner during a read, a write and an empty write waited out, and each caller ended with `Fault("callee was killed")`, which the runtime reports on standard error. So the regression test kills a session of `cat` whose helpers wait and holds that both return. A helper caught in a call is left untested, since the fault's report would stand in the test run.

The two events take two names, `ReaderSessionEnded` and `WriterSessionEnded`, where the shell's reader takes `ShellEnded`: a module's constructors are unique across its types (report §4.2). Each is named for its helper's session, which keeps the form of an end's name. One type for both helpers was weighed and left out, since a reader's type would then admit a `Write` it never takes (principle 3). `make test` takes 18 s as before, for one more case.

The test of a write waited out started its writer by `writing`, a writer the program never starts, and starts it by `startWriting` now, so that every test runs a helper as `serve` spawns it.
