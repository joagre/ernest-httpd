13. **A program with a module named `Shell` cannot have a shell attached.** A node whose program has a module `Shell`, `item6-probes/clash/shell/src/shell.ern`, one `main` that sleeps, listed both ways with an `ops` directory, refuses `ern shell --config-dir ops --attach node-shell` with `the node node-shell runs another build of ern than this shell; attach with its release`, status 1, the same build on both sides; the node says `the peer ops's spawn at Shell.localHalf:2015 was not loaded: this node could not load Shell: its back end could not compile it, {emitter_defect,none, "the link places no {named,['Shell','Session']} in a unit"}`. The same program with the module named `Session` or `Waiter` attaches and `:processes` lists it; ernest-httpd, whose `Shell` is design §11's, fails the same way. Principle 5: a feature costs a program that does not use it nothing, not even a name; principle 3: the refusal names a wrong cause. Ask: the toolchain's own modules stand where no module name of a program reaches them, and an attach whose spawn could not be loaded says so. Nothing here renames the module.

14. **E.18 says nothing of the dual stack.** `Tcp.listen("0.0.0.0", p)` and then `Tcp.listen("::", p)`, in either order, answers `Left(Other("address already in use"))`, and on a `::` listener `Tcp.remote` of an IPv4 client reads `::ffff:127.0.0.1`: `item6-probes/dual/src/dual_probe.ern`. E.18 has `"0.0.0.0"` and `"::"` as every interface of a family, so a reader predicts a listener of each beside the other, as the proposal planned, and meets the refusal at the start. Principle 1; principle 3 for the address that changes form. Ask: E.18 states that `"::"` takes IPv4 too where the host's `bindv6only` is 0, that `"0.0.0.0"` on the same port is then refused, and that an IPv4 client's host reads `::ffff:` and its address; or `listen` takes a way to listen on IPv6 alone.

15. **§11.3 says nothing of `--peer-dir` between two users of one machine.** A configuration directory opens to its owner alone, and `--peer-dir` reads the peer's directory as a node reads its own, so a service's node and its operator, two users, cannot list each other by `ern config --peer-dir` from their own accounts; the deployment makes both directories as the superuser and gives each to its user, which the guide's §1.1 allows and does not say. Not probed here, with no second user. Principle 3: the attached shell's own use is left unsaid. Ask: the guide says how a node run as a service's user and its operator list each other, the superuser's way or one of `ern config`'s own.

16. **A process that waits keeps what it has dropped.** A connection that wrote a 1 MiB response and waits idle holds about 2 MiB over plain HTTP and 3.1 to 3.8 MiB over TLS, read as the node's VmRSS against the kernel's send queues, which hold the response whole, and gives it back only when the connection ends: `measure/`, 100 connections that read nothing. Inferred from the numbers, not from a page. Principle 3: memory a program dropped, held where nothing shows it. Ask: §10 or E.21 says when a waiting process's dropped values are reclaimed, or the runtime collects a process as it begins a long wait.
