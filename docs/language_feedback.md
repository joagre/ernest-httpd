28. **At the limit of open files `Tcp.accept` answers at once, with no connection waiting, and E.18 does not say so.** E.18 has `accept` wait for a connection within its milliseconds, and §12 says that an operation that would open a file beyond the limit answers `Left(Other("too many open files"))`. The host takes the descriptor before it waits for a connection.

    So an acceptor that asks again at once spins at the limit, and a server's `cannot accept` comes as its table fills, before any connection is turned away. ernest-httpd's server under `ulimit -n 64` showed it: the connection that filled the table was accepted and answered, and none waited when the line came. RFC 3986 writes none of `"`, `<`, `>`, `[` and `]` outside an IP literal, `\`, `^`, `` ` ``, `{`, `|` and `}`. So `parseRequest` reads `GET /?a[]=1 HTTP/1.1`, `GET /a|b HTTP/1.1` and `GET /?q={x} HTTP/1.1`, and `target` answers `None` for each; a probe on `ern 0.10.0` shows both.
